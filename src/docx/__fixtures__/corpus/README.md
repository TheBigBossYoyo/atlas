# DOCX round-trip fidelity corpus

Plan tasks: **P0.5** (findings **QA-09**, **DXS-17**).
See `.sisyphus/plans/atlas-phase3-improvement.md` (P0.5) and
`.sisyphus/plans/atlas-phase3-findings-register.md` for the full task text
and evidence this corpus exists to guard against.

## What this is

Thirteen small, synthetic `.docx` fixtures, each built to exercise one
real-world OOXML feature (named styles, headers/footers, footnotes and
endnotes, table grids and merged cells, a banded table style, inline and
anchored images, multi-level lists, hyperlinks and bookmarks, threaded
comments, tracked changes, mixed section breaks, and a content control next
to an `mc:AlternateContent` shape). They're consumed by
`src/docx/__tests__/roundtrip.corpus.test.ts`, which round-trips each one
through `loadDocx` → `saveDocx` (both as a no-op and after a trivial edit)
and asserts the result is still a valid, OPC-consistent package with an
unchanged document structure.

LibreOffice is not installed in this environment (see the P0.5 task's
baseline notes), so there are no reference renderings to compare against —
only the structural/XML-level assertions the test file describes. See
**Adding real-world documents** below for how to extend this once a
LibreOffice (or real Word) install is available.

## Regenerating the fixtures

```
node scripts/generate-docx-corpus.mjs
```

This overwrites every `.docx` file in this directory. The generator is
deterministic — re-running it with the same `docx`/`jszip`/Node versions
reproduces byte-identical files — achieved by:

- building each fixture with the `docx` npm package wherever it can express
  the feature natively, falling back to direct XML injection
  (`scripts/lib/corpusArchive.mjs`) for the handful of constructs it can't
  (a content control / `w:sdt`, an `mc:AlternateContent` shape, a comment
  reply's `w:parentId`, and a custom table style's `w:tblStylePr`);
- pinning every timestamp `docx` or JSZip would otherwise fill in with
  `new Date()` (`docProps/core.xml`, comment/revision dates, zip entry
  mtimes) to a fixed instant;
- renaming `docx`'s randomly-generated (nanoid) external-hyperlink
  relationship ids to a stable, order-based scheme; and
- generating embedded images as tiny solid-color PNGs from raw pixel data
  at generation time (`scripts/lib/corpusPng.mjs`) rather than checking in
  binary assets.

If you add a fixture, also add its id to `FIXTURE_IDS` in
`src/docx/__tests__/roundtrip.corpus.test.ts` — a small sanity test asserts
the two lists match, so a forgotten entry fails loudly instead of silently
skipping a fixture.

## Known failures

A handful of fixture+mode combinations fail against `main` today for
reasons already tracked in the findings register; they're encoded as
`it.fails(...)` (with the finding id in the test title) in
`roundtrip.corpus.test.ts` rather than skipped, so the suite stays green
now and — because a `.fails` test that starts *passing* is itself reported
as a failure — flips the moment the underlying bug is fixed, telling
whoever fixed it to promote that case back to a plain `it`:

- `footnotes-endnotes` and `header-footer-page-numbers` (**DXS-01**): the
  footnote/footer/header/endnote parsers currently stash each part's body
  as a single opaque `UnknownNode` ("Option B"), and the corresponding
  serializers refuse to write anything but paragraph blocks into a
  standalone part — so saving throws. Note this isn't limited to documents
  that visibly use footnotes: `docx` (like real Word) always emits a
  `footnotes.xml`/`endnotes.xml` containing boilerplate separator entries,
  so *every* fixture would hit this if left alone —
  `scripts/lib/corpusArchive.mjs`'s `stripAutoGeneratedFootnotesEndnotes`
  strips that boilerplate from the other 11 fixtures so their failure
  surface stays about the feature they actually exercise.
- `table-fixed-grid-merged-cells` and `table-styled-banded` (**DXS-02**):
  `w:tblGrid` is parsed and then silently dropped rather than re-emitted,
  so a table's explicit column grid disappears on save.

## Adding real-world documents and reference renderings

This corpus is synthetic by design (no representative real-world documents
were available within this task's scope, and LibreOffice isn't installed
here to render references). To extend it later:

1. **Real-world documents.** Drop additional `.docx` files into this
   directory (real documents with permission to redistribute, or
   publicly-available OOXML conformance-suite samples — e.g. the OOXML SDK
   sample files or Apache POI's test fixtures — work well as a fallback).
   Keep them small; add their id to `FIXTURE_IDS` in
   `roundtrip.corpus.test.ts` per the note above. Prefer files that isolate
   one feature at a time the way the synthetic fixtures do — it makes a
   failure's cause obvious instead of needing to guess which of several
   features in a large real document triggered it.
2. **Reference renderings.** Once a LibreOffice (or real Word) install is
   available, generate a reference PNG per fixture with:
   ```
   soffice --headless --convert-to png --outdir src/docx/__fixtures__/corpus/reference-screenshots <fixture>.docx
   ```
   Store the output under `reference-screenshots/<fixture-id>.png` next to
   this README. A future visual-regression task can then render each
   fixture through Atlas's own `DocxRenderer` and diff it against that
   reference — this corpus and its round-trip harness only assert
   structural/XML fidelity, not pixel-level rendering fidelity.
